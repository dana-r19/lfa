# Laboratory Work: Lexer & Scanner
Course
Formal Languages & Finite Automata

Author
Romanov Dana

Objectives
This laboratory work has three main objectives. The first objective is to understand what lexical analysis is and why it represents a fundamental stage in compilers and interpreters. The second objective is to get familiar with the inner workings of a lexer, scanner, or tokenizer, including how it processes raw character streams and produces structured tokens. The third objective is to implement a sample lexer that demonstrates these concepts in practice, going beyond a simple calculator to include features like floating-point numbers, trigonometric functions, and comparison operators.

Implementation Description
Overview
The implemented lexer provides tokenization for a Mini-Math Language that significantly exceeds the basic calculator requirement. This language supports integer and floating-point literals, arithmetic operators including addition, subtraction, multiplication, division, and power, trigonometric functions such as sine, cosine, and tangent, variable identifiers, comparison operators including equality, inequality, less than, and greater than, the assignment operator, parentheses and commas for function arguments, and single-line comments. The lexer ignores whitespace and comments while accurately tracking line and column positions for potential error reporting.

Lexer Architecture
The lexer follows a regex-based deterministic finite automaton approach. The token specification is stored as a list of regular expression patterns, each associated with a specific token type and an optional value transformer. These patterns are compiled into a single master regular expression using named groups, which allows the lexer to scan the input in a single pass from left to right. At each step, the lexer matches the longest possible pattern starting from the current position, determines the corresponding token type, transforms the string value if necessary (for example converting the string "42" into the integer 42), updates the line and column counters based on newlines and character positions, and then emits the token. When whitespace or comments are encountered, the lexer simply skips them and continues to the next token without producing output. This process repeats until the end of the input is reached, at which point an EOF token is emitted.

Key Components
The Token class is implemented as a dataclass containing four fields: the token type from an enumeration, the actual lexeme value, the source line number where the token appears, and the column position within that line. This structure preserves all necessary information for subsequent compilation stages.

The Lexer class maintains the source code as a string, the current position index, the current line number, and the current column number. The token specifications are stored as tuples containing a regex pattern, a token type, and a transformer function. The master regex is compiled during initialization using the verbose flag for readability. The keywords dictionary maps function names like sin, cos, and tan to their respective token types, allowing the lexer to distinguish between variable identifiers and built-in functions.

The core algorithm is implemented in the get_next_token method. This method first checks if the position has reached the end of the source, returning an EOF token if true. It then attempts to match the master regex against the source starting at the current position. If no match is found, an unexpected character is encountered, so an ERROR token is emitted and the position advances by one character. If a match succeeds, the lexer updates the position to the end of the matched text, counts the number of newlines within the matched text to adjust the line number appropriately, and updates the column number based on the last line of the match. The token type and value are then determined by examining which pattern produced the match. For identifier patterns, a check against the keywords dictionary determines whether the token is a function name or a variable. For all other patterns, the transformer function converts the string to the appropriate data type. If the token type is None indicating whitespace or a comment, the lexer recursively calls itself to get the next token. Otherwise, a new Token object is returned with all the collected information.

The tokenize method provides a convenient wrapper that repeatedly calls get_next_token until EOF or an error is encountered, collecting all tokens into a list for easier processing.

Features Beyond Basic Calculator
The implemented lexer offers several features that go beyond a simple calculator. Floating-point numbers are recognized through the pattern that matches digits followed by a decimal point and more digits, and these are automatically converted to Python float objects. The power operator using the caret symbol is supported alongside the basic arithmetic operators. Trigonometric functions sin, cos, and tan are treated as distinct token types rather than variable identifiers. Comparison operators including double equals for equality, exclamation equals for inequality, and the standard less than and greater than symbols are all recognized. Variable names consisting of letters, digits, and underscores with the constraint that they cannot start with a digit are supported. Comments beginning with two forward slashes are completely ignored by the lexer, as are all whitespace characters including spaces, tabs, and newlines. Line and column tracking ensures that each token knows exactly where it appeared in the source code, which is valuable for error messages in later compilation phases.

Example Run
When given the input string "x = 3.14 + sin(45)", the lexer produces a sequence of tokens. The first token is a VARIABLE token with the value 'x' appearing at line 1 column 1. The second token is an ASSIGN token with the value '=' at line 1 column 3. The third token is a FLOAT token with the numeric value 3.14 at line 1 column 5. The fourth token is a PLUS token with the value '+' at line 1 column 10. The fifth token is a SIN token with the value 'sin' at line 1 column 12. The sixth token is an LPAREN token with the value '(' at line 1 column 15. The seventh token is an INTEGER token with the value 45 at line 1 column 16. The eighth token is an RPAREN token with the value ')' at line 1 column 18. Finally, the EOF token is emitted with a None value at line 1 column 19. Each token carries complete positional information, and numeric literals are already converted from strings to their appropriate numeric types.

Conclusions
This laboratory work successfully demonstrates a comprehensive understanding of lexical analysis and its practical implementation. The theoretical understanding is confirmed by the fact that lexical analysis converts raw character streams into meaningful tokens, forming the first and most fundamental phase of compilation. The practical implementation shows that a regex-based deterministic finite automaton approach provides an efficient and readable lexer that can be extended with minimal effort. The extensibility of the design means that adding new operators, keywords, or literal types requires only adding new entries to the token specifications list without rewriting any core logic. The error handling capabilities allow the lexer to gracefully handle unexpected characters by emitting ERROR tokens while maintaining accurate position tracking throughout the process. The implemented lexer goes beyond the basic calculator requirement by supporting floating-point numbers, the power operator, trigonometric functions, comparison operators, variables, and comments, thereby demonstrating a robust understanding of lexical analysis principles that are directly applicable to real-world programming languages.

References
The first reference is the classic compiler design textbook "Compilers: Principles, Techniques, and Tools" by Aho, Sethi, and Ullman, which provides foundational knowledge of lexical analysis. The second reference is the study of regular expressions and their application in lexical analysis, particularly how deterministic finite automata can be constructed from regular expressions. The third reference is the Python re module documentation, which was used for implementing the regex-based pattern matching in this lexer.
